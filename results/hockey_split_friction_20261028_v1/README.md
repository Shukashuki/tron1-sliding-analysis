The native PhysX wheel materials now support an opt-in unequal pair. The first setting is **mu_static = 0.9, mu_dynamic = 0.7**, an exploratory sensitivity setting, not identified TRON1 tire data. The existing equal-coefficient recipe remains reproducible in its archived snapshots. The new [full-length protocol](../../config/hockey_bilateral_split_friction_v1.json) inherits the last bilateral reward recipe to isolate the material change; it has not been trained and does not resolve that recipe's previously observed early falls by construction.

A single-environment GPU 7 probe completed **16 control steps / 128 physics steps** at 50/400 Hz using the previous original-speed hockey actor. Live PhysX readback was 0.899999976 static and 0.699999988 dynamic for both wheels; the ground remained unit-friction multiply with zero restitution. The actor was reused remotely, not uploaded or retrained. This verifies coefficient installation and short execution only. It does not establish full-horizon success, breakaway thresholds, a static-to-dynamic transition, or improvement over the baseline. ## Implementation and capacity interpretation

`static_dynamic_friction_ratio = 9/7` is passed from the hockey protocol into the startup material event. Dynamic friction retains the existing draw `U(0.3, 1.2)` for any future training with this protocol; static friction equals `(9/7) * mu_dynamic`, giving a static range of approximately `[0.3857, 1.5429]`. One draw is shared by both wheels and every collision slice. Nonwheel materials, disturbances, controller observations and actuator settings are unchanged. Evaluation uses the fixed 0.9/0.7 pair. Material readback audits both columns independently. The legacy scalar `mjlab_recipe_mu` explicitly remains the dynamic coefficient.

For an idealized contact, the sticking bound is `||F_t|| <= mu_static F_n`, while sustained Coulomb sliding is approximately `F_t = -mu_dynamic F_n v_t/||v_t||`. PhysX implements contact-patch friction through anchors and iterative constraints; these equations are not an exact solver-mode detector. NVIDIA documents distinct static/dynamic coefficients and differences between PGS and TGS friction processing in [Rigid Body Dynamics](https://nvidia-omniverse.github.io/PhysX/physx/5.4.1/docs/RigidBodyDynamics.html#friction-and-restitution).

The analyzer now records both `rho_static = ||F_t||/(mu_static F_n)` and `rho_dynamic = ||F_t||/(mu_dynamic F_n)` only for touching wheels with positive normal force. A ratio above one relative to dynamic capacity can still be within static capacity. Neither ratio alone identifies sliding or proves a solver transition. Continue checking geometric contact, material-point tangential velocity and opposing/dissipative force. These are wheel-aggregate indicators; separate friction anchors may cancel in the aggregate, and their individual normal loads are not available from this readback. The existing boundary-sliding reward continues to use dynamic capacity, with geometric contact and sliding gates; no force information is added to the actor.

## What can be changed

| Option | Current implementation | What it changes and what remains missing |
| --- | --- | --- |
| Native rigid cylinder, unequal coefficients | New material setting tested above | Static/dynamic capacity; the native contact law and rigid wheel stay in place |
| Nine adjacent axial cylinders | Existing `tron1_wheel_geometry.py`; unequal-pair allocation tested for all 18 wheel shapes | Contact representation and possible patch/anchor distribution; same radius, total width, wheel mass/inertia and joints. No elastic tread or independent suspension is created |
| External nonlinear tire force | Existing `nonlinear_tire_torch.py` / `physx_batched_tire.py` | Simplified isotropic combined-slip Magic-Formula-style curve; native normal response retained, native wheel tangential friction disabled to avoid double counting. One preceding-step load/point is used, giving 2.5 ms explicit coupling delay. No static adhesion, bristle memory, identified camber thrust, or fitted tire parameters |
| Stateful brush / elastic slices | Proposed next model, **not implemented or calibrated here** | Tangential deformation and stored contact history, separate breakaway/sliding capacities, local load/slip and their moments; requires force-law and normal-load/discretization decisions |

The [previous wheel-model experiments](../2026-10-25-wheel-contact-model-comparison.md) already evaluated cylinder, nine-slice and nonlinear variants for the turning task. They did not solve continuous support. Their older force-based any-wheel criterion must not be substituted for the current full-horizon bilateral geometric criterion.

For a stateful brush, a possible constitutive starting point is `F_trial = -K_t xi - C_t v_t`, with tangential displacement `xi` carried between valid contact updates. The sticking trial is limited by static capacity; sliding uses a dynamic-capacity law with an explicit return/projection and dissipative direction. Contact loss must invalidate/reset the relevant history. A rolling brush also needs material-point transport/replacement and a relaxation model; merely integrating slip at a moving contact minimum is insufficient. Per-slice forces satisfy their own load-scaled limits, and total force/moment are `sum(F_i)` and `sum(r_i cross F_i)`. Each slice uses its own normal load; assigning the entire wheel load to every slice would multiply the available friction incorrectly. For native friction patches, pointwise load allocation must first be measured or explicitly modeled.

A PhysX Vehicle tire has longitudinal/lateral stiffness, combined-force saturation, camber contribution and a friction-versus-slip curve, as described in [NVIDIA's Vehicle documentation](https://nvidia-omniverse.github.io/PhysX/physx/5.6.1/docs/Vehicles.html). That is a separate vehicle pipeline, not an automatic material upgrade for the TRON1 articulation. The current external-force prototype is also not that Vehicle implementation.

Changing the core solver is a separate level of work. Time step, PGS/TGS, iterations and contact/friction-patch distances can be studied with the native law. In particular, [`frictionOffsetThreshold` is a contact separation distance and `frictionCorrelationDistance` controls anchor merging](https://nvidia-omniverse.github.io/PhysX/physx/5.4.1/_api_build/classPxSceneDesc.html); neither is a user-defined slip-speed threshold or tire-force curve. C++ contact modification/core changes require a different integration path; the [PhysX GPU documentation](https://nvidia-omniverse.github.io/PhysX/physx/5.4.0/docs/GPURigidBodies.html) notes that contact-modified pairs use CPU contact generation. No such solver rewrite or new compilation is performed here.

## Controlled next comparison

The [comparison plan](../../config/hockey_contact_model_comparison_v1.json) separates coefficient, geometry and force-law changes. Start with the same reference, initial state and actor for cylinder 0.7/0.7 versus cylinder 0.9/0.7; then compare cylinder versus nine slices at 0.9/0.7 with matched offsets and inertial properties. A brush arm needs its own implementation/identification first. Retain a native/external regularized-Coulomb control when comparing custom nonlinear laws to distinguish curve changes from explicit coupling delay. At least two physics step sizes should be checked for the external-force implementation.

Whole-horizon bilateral contact remains the first task gate. Then compare speed, stopping distance, XY error, tilt, per-wheel slip, both capacity ratios, dissipative power and discontinuities. Unequal coefficients can change stick/slip transitions and may also increase chatter; they do not guarantee stable contact or repair the reward/reset issue in the failed policy. Full retraining and complete new-policy validation have not started.
